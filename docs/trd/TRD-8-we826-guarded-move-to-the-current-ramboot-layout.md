# TRD-8: WE826 guarded move to the current ramboot layout

Implements [ADR-002](../adr/002-flash-constrained-units-boot-from-the-relays-mirror.md), decision 5 (the move of an in-service unit through the relay, with no SSH), for the WE826. Status: Planned: the script, the `rundev.sh` branch, the tests and the docs are built (slices 1 to 3); the bench run and the field run on Bus 01 are not. (TRD-7 is the number ADR-007 names for its option B, so this is TRD-8.)

## 1. Objective

A ZBT WE826-Q-WD that cannot take a managed upgrade moves once, through the relay and with no SSH, onto the current `ramboot` layout and a current release, with a rollback that needs neither the network nor a person; from then on every release reaches it by managed rollout (`docs/upgrade.md`).

The unit that needs it is Bus 01 (Concord Tours), `WE826-F85E3CD01310`: sctl 0.6.2.142 (`a9227a8`) since 2026-09-08. An agent before 0.6.7 has no `POST /api/upgrade`, and the unit has no `install.json`, so the fleet cannot ask it. It is a bus: when the new agent does not come up, nothing restarts sctl until the next ignition and nobody can reach the unit, so the move must put the old agent back by itself. A WE826 installed by 0.6.7 or 0.6.8 (an `install.json` without `helper_prefix`, whose helper cannot start under the musl loader, ADR-002 section 2) takes the same move.

## 2. What a 0.6.2-era WE826 has

From the history of `devices/` (2026-05-31 to 2026-10-01) and the field records of Bus 01:

- `/etc/init.d/sctl`: the shared `devices/common/sctl-ramboot.init`. Bus 01 carries `c97ad7a`'s (supervised, log cap; SHA-256 `f0b8c0b8...`) since 2026-08-16, byte for byte today's file. An older unit may carry the single-shot init of 2026-05-31 or `8be5f2b`'s supervised one. There is no procd: `start` runs a shell loop that starts the wrapper and respawns it 10 s after it exits; pid files `/var/run/sctl-supervisor.pid` and `/var/run/sctl.pid`; log `/tmp/sctl/ramboot.log`. `stop` kills the supervisor with TERM, then the daemon (TERM, then KILL after 1 s). The single-shot init knows no supervisor.
- `/etc/sctl/ramboot.sh`: the bring-up's (2026-08-07), never replaced on Bus 01 since. Every version before `c97ad7a` checks `MIN_TMP_KB` (24 MB) of free `/tmp` at every start, cached payloads or not; today's checks only when it must download. Every version keeps the payloads in `/tmp/sctl/cache/{sctl-server,sctl-comms,musl-libc,libgcc}.payload` and trusts a cached one by its SHA-256 only.
- `/etc/sctl/ramboot.conf`: `install.sh`'s keys (`RUN_DIR`, `CACHE_DIR`, `BIN`, `PLUGIN`, `MUSL_LIBC`, `LIBGCC`, `SCTL_CONFIG`, a URL, SHA-256 and gzip flag for each of the four payloads, `MIN_TMP_KB`, `FETCH_TIMEOUT_SECS`, `CONNECT_TIMEOUT_SECS`, `FETCH_ATTEMPTS`, `FETCH_RETRY_SECS`, `ALLOW_UNSIGNED`). On Bus 01 `FETCH_ATTEMPTS=60`, and the URLs name the relay by IP (`http://174.138.114.209:8081/...`: the bus's resolver timed out on the name).
- `/etc/sctl/sctl.toml`: the unit's key and serial, `[comms]` and `[lte]`, the `[tunnel]` block; on Bus 01 also `state_dir = "/etc/sctl/state"`, which holds the Infra targets and credentials.
- No `/etc/sctl/install.json`.
- In RAM: the four cached payloads, the expanded `/tmp/sctl/sctl-server` and `/tmp/sctl/lib/{libc.so,libgcc_s.so.1,libsctl_comms_quectel.so}`; the agent runs as `/tmp/sctl/lib/libc.so --library-path /tmp/sctl/lib /tmp/sctl/sctl-server serve`.
- BusyBox on uClibc: no `sha256sum` (`openssl dgst -sha256` is used), no `setsid`, `start-stop-daemon` present, `curl` present.

What the current install writes beyond that: today's `ramboot.sh` (the cache gate; it also starts `netage-wanpref` when that init exists, which the move does not install), `install.json` (`{"v":1,"layout":"ramboot","target":"mips_24kc","helper_prefix":["/tmp/sctl/lib/libc.so","--library-path","/tmp/sctl/lib"]}`), and a `ramboot.conf` naming the release's files on the relay's mirror.

## 3. Deliverables

- `devices/we826-qwd/ramboot-refresh.sh <version> [wait_secs]`, BusyBox ash and uClibc safe, run detached from its stage, reporting one word in `<stage>/state` (`started`, `fetching`, `installing`, `restarting`, `rolling_back`, then `done`, `rolled_back`, `failed` or `needs_hands`) and logging to `/tmp/sctl-we826-refresh.log`:
  1. checks every staged file against `files.sha256` and parses the shell ones;
  2. recognises the layout of section 2 or refuses (`failed`, nothing touched, no fetch): the shared ramboot init, a `ramboot.conf` naming the four payloads with every path the one the current layout uses, `sctl.toml`, no `install.json` (or a `ramboot`/`mips_24kc` one without `helper_prefix`), no `/etc/sctl/disabled`, the musl loader in `/tmp/sctl/lib`, and the running agent answering `/api/health` with its version; it logs which released init and `ramboot.sh` it found;
  3. requires `/tmp` free at least 24 MB and the old `MIN_TMP_KB`, and 64 KB on the overlay;
  4. fetches the four new payloads into a work directory and verifies each SHA-256; copies the four old ones to RAM, verified against the old `ramboot.conf` (fetched from the old URLs when the cache no longer holds them);
  5. runs the new server through the new loader: `--version` must print the version, `target` must print `mips_24kc`, and `install-info --config /etc/sctl/sctl.toml` with `SCTL_INSTALL_JSON` on the staged file must parse both and report `ramboot` with the loader prefix;
  6. copies the init, `ramboot.sh`, `ramboot.conf`, `sctl.toml` and `install.json` (when present) to `/tmp/sctl-we826-refresh-rollback` with their SHA-256s;
  7. stops the old agent with the init that started it and makes sure it is gone (its pids, then `/api/health` silent); writes `ramboot.sh`, the init, `install.json` and `ramboot.conf` last, each beside its target and renamed over it, and checks what landed; moves the new payloads into the cache; starts the new init once;
  8. healthy is `/api/health` answering the version and, when `sctl.toml` has a `[tunnel] url`, a connected tunnel, twice in a row, 5 s apart, within `wait_secs` (300 by default);
  9. otherwise stops the new agent with the new init, puts back every file (removing `install.json` when there was none) and the old payloads in the cache, checks each against its recorded SHA-256, starts the old init and waits for the old version to answer (a second start if it does not): `rolled_back`, or `needs_hands` when the restore was incomplete or the old version never answered.
  `sctl.toml` is never written. The new `ramboot.conf` keeps the unit's `MIN_TMP_KB`, `FETCH_*` and `CONNECT_TIMEOUT_SECS`, and the log names any old key it does not carry.
- `devices/we826-qwd/refresh-stage.sh <release.json> <mirror base> <out dir>`: writes the stage (the current init and `ramboot.sh`, the `ramboot.conf` for the release's four `mips_24kc` files on that mirror, `install.json`, the script, `files.sha256`) from a manifest already verified.
- `rundev.sh device upgrade-remote <name> <version> <user@relay | mirror URL>`: the layout probe answers `we826` (ramboot through the musl loader, no `install.json` naming it) and `we826-managed` (refused: a rollout citizen); every other answer is unchanged. The WE826 path reads the version's `release.json` and its signature from the mirror (from the relay's listing when given `user@relay`), checks the signature against the keys the agent embeds (`server/src/upgrade/keys.rs`; `SCTL_TRUST_KEY` adds a bench key), checks the version and that the mirror serves the four payloads with the manifest's SHA-256s, refuses a unit whose health reports another target or a layout, stages the files through the file API, launches the script in its own session (`start-stop-daemon -b`, else `setsid`, else a background job; never with a signal ignored), follows the state file to the outcome (`WE826_WATCH_SECS`, 1800 s), prints the log tail on `failed` or `rolled_back`, and after `done` checks that health reports the version, layout `ramboot` and target `mips_24kc`.
- Tests: `devices/we826-qwd/tests/ramboot-refresh-test.sh` and `upgrade-remote-test.sh` (section 5).
- `docs/upgrade.md` (the `ramboot` row, "A WE826 installed before 0.6.7", "By hand"), `devices/we826-qwd/README.md`, `CHANGELOG.md` `[Unreleased]` (CRLF), this TRD and its index rows.

## 4. Decisions inside the move

- **A rollback needs no network.** The old payloads are kept in RAM, verified, until the move is settled, and put back in the cache before the old init starts, so the old `ramboot.sh` starts from cache. The bus is mobile: the moment the new agent fails is the moment its link may be gone too. ADR-002 section 5 rejects keeping two payload sets in the steady state; this copy lives only during the move and is removed at `done` (the small files stay in `/tmp` until the next boot).
- **Stop with the init that started it, start with the init that will own it.** A `restart` through the new init would kill the old agent correctly, but a rollback's restart through a single-shot old init would leave the new init's supervisor running, and it would respawn the new version.
- **No signal is ignored, by the script or its launcher.** The init's supervisor is a shell started from the script; a signal ignored there is inherited, ash cannot trap a signal ignored on entry, and `stop` (TERM) would no longer stop sctl; the agent's sessions would inherit an ignored HUP too. The script catches HUP and TERM with a handler (reset to the default in anything it execs) and is detached in its own session, so the agent's exit cannot take it down. (On the RUT241, procd starts the service, so its launcher's `trap "" HUP TERM` is harmless there.)
- **`ramboot.conf` last.** It is the file that switches the version. A power cut during the writes boots the old version until it is renamed, the new one after; every file is renamed whole.
- **The new binary reads this unit's configuration before anything moves.** `install-info` parses `sctl.toml` and `install.json` with the new version's types; `validate()` runs only at `serve`, so a configuration the new agent parses but refuses to serve is caught by the health check and rolled back.
- **An unfinished move blocks the next one.** `/tmp/sctl-we826-refresh-rollback/in-flight` exists from the stop to the outcome (and stays after an incomplete restore): a later run refuses rather than replace that backup.
- **Not built:** a separate dead-man process. The script is detached in its own session and shares nothing with the agent it stops; what it does not survive (a power cut) reboots the unit into a consistent layout. A soak after `done` is the managed path's job for later releases.

## 5. Verification

- `devices/we826-qwd/tests/ramboot-refresh-test.sh`: the script runs for real against a unit as a directory tree (the 0.6.2-era files, payloads in the cache, a fake init that does what `ramboot.sh` does from the cache only and records any download it would need, a fake mirror and `/api/health`, gzipped shell scripts as payloads and a loader that execs its program). Every case runs under BusyBox ash (the unit's shell) and under dash with the WE826's tools only (no `sha256sum`, `setsid` or `mktemp`: the `openssl` path). Cases: the happy path (files, modes, kept settings, stop with the old init and start with the new, no download at start); a payload hash mismatch (nothing changed, the old agent never stopped); six unknown layouts (another `BIN`, no musl payload, a `gz-tmp` `install.json`, an `install.json` that already names the loader, another init, `disabled`: refused before any fetch); the new agent never healthy (tunnel down) and healthy once only: rolled back, every file and payload byte for byte with its mode, the old version running, no download needed; old payloads no longer cached (fetched before anything moved; refused when they cannot be); the probe (an `sctl.toml` the new server cannot read; a payload that is not the version asked for); the guards (`/tmp`, overlay, no agent answering, a staged file changed in transit, an unfinished earlier move, a second launch). 107 passed (2026-10-09).
- `devices/we826-qwd/tests/upgrade-remote-test.sh`: the WE826 function as it is in `rundev.sh`, with the mirror, the relay's exec and file routes and `start-stop-daemon` faked, a release signed with a key made in the test: done end to end (the device list records the version), rolled back with the log tail, an unsigned manifest, a mirror serving a wrong payload, a manifest of another version and a unit reporting a layout refused before the device is touched. 14 passed (2026-10-09). `install-test.sh` (15) and `wanpref-test.sh` (19) unchanged and green.
- **Bench, the ZBT WE826 (when it is back on the bench):** installed as Bus 01 is (`v0.6.2`'s `install.sh` with the `a9227a8` payloads, or the bring-up's files, plus `state_dir`); before the move, the read-only checks of the field run below. Then `rundev.sh device upgrade-remote zbt <current version> http://174.138.114.209:8081/artifacts/<current version>`: `done`, health reports the version, layout `ramboot`, target `mips_24kc`; a reboot comes back on the new version from the mirror. A forced rollback on a fresh 0.6.2 install (`WE826_WAIT_SECS=10`, which no tunnel reconnect meets, or the bench relay stopped once the state reads `restarting`): `rolled_back`, files byte for byte, 0.6.2 answering, the cache holding the old payloads. A refused move (a bundle signed with a bench key, `SCTL_TRUST_KEY`, whose server prints another version): `failed` at the probe, nothing changed, the agent never stopped. A power cut while `installing` (pull the plug after `state: installing` shows): the unit boots one version or the other, whole. Then the first managed upgrade from the fleet to a bench bundle: `done`/`ok`.
- **Field, Bus 01, with the owner present:** the bus online on its wire (Starlink through the Peplink), parked, ignition held for the run; the relay holding the version complete with its mirror by IP and the `a9227a8` payloads still served. First, read-only through the relay: `sha256sum` (`openssl dgst -sha256`) of the init and `ramboot.sh`, `cat /etc/sctl/ramboot.conf`, `ls -l /tmp/sctl/cache`, `df -k /tmp /overlay`, `grep -c '^\[tunnel\]' /etc/sctl/sctl.toml`, recorded here; they must match section 2 or the move is not run. Then `rundev.sh device upgrade-remote bus01 <version> http://174.138.114.209:8081/artifacts/<version>`, the log kept. After `done`: the fleet lists Bus 01 with target `mips_24kc` and layout `ramboot`, the eight Infra targets survive (they live in `state_dir`), and the next ignition boots the new version from the mirror. After `rolled_back`: the log says why, Bus 01 answers on 0.6.2.142, and the cause is fixed before another run. After `needs_hands`: the owner is there; the old files are in `/tmp/sctl-we826-refresh-rollback` until the next boot.
