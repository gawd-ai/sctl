# TRD-8: WE826 guarded move to the current ramboot layout

Implements [ADR-002](../adr/002-flash-constrained-units-boot-from-the-relays-mirror.md), decision 5 (the move of an in-service unit through the relay, with no SSH), for the WE826. Status: Implemented (2026-10-10): Bus 01 moved to 0.6.11.196 on the current ramboot layout (slice 5); the bench run on the ZBT (slice 4) was skipped by the owner's choice, since the unit is with a technician. (TRD-7 is the number ADR-007 names for its option B, so this is TRD-8.)

## 1. Objective

A ZBT WE826-Q-WD that cannot take a managed upgrade moves once, through the relay and with no SSH, onto the current `ramboot` layout and a current release, with a rollback that needs neither the network nor a person, and with flash never switched to a version that has not proved itself on the unit; from then on every release reaches it by managed rollout (`docs/upgrade.md`).

The unit that needs it is Bus 01 (Concord Tours), `WE826-F85E3CD01310`: sctl 0.6.2.142 (`a9227a8`) since 2026-09-08. An agent before 0.6.7 has no `POST /api/upgrade`, and the unit has no `install.json`, so the fleet cannot ask it. It is a bus: when the new agent does not come up, nothing restarts sctl until the next ignition and nobody can reach the unit, and an ignition cycle can come at any moment, so the move must put the old agent back by itself and every flash state it passes through must boot. A WE826 installed by 0.6.7 or 0.6.8 (an `install.json` without `helper_prefix`, whose helper cannot start under the musl loader, ADR-002 section 2; its agent reports layout `ramboot`) takes the same move.

## 2. What a 0.6.2-era WE826 has

From the history of `devices/` (2026-05-31 to 2026-10-01) and the field records of Bus 01:

- `/etc/init.d/sctl`: the shared `devices/common/sctl-ramboot.init`. Bus 01 carries `c97ad7a`'s (supervised, log cap; SHA-256 `f0b8c0b8...`) since 2026-08-16, byte for byte today's file. An older unit may carry the single-shot init of 2026-05-31 or `8be5f2b`'s supervised one. There is no procd: `start` runs a shell loop that starts the wrapper and respawns it 10 s after it exits; pid files `/var/run/sctl-supervisor.pid` and `/var/run/sctl.pid`; log `/tmp/sctl/ramboot.log`. `stop` kills the supervisor with TERM, then the daemon (TERM, then KILL after 1 s). The single-shot init knows no supervisor. The wrapper runs from the supervisor with its environment, so `SCTL_RAMBOOT_CONFIG` given to `start` reaches it.
- `/etc/sctl/ramboot.sh`: the bring-up's (2026-08-07), the 2026-05-31 file (`3e5eea75...`), never replaced on Bus 01 since. Every version before `c97ad7a` checks `MIN_TMP_KB` (24 MB) of free `/tmp` at every start, cached payloads or not; today's checks only when it must download. Every version reads `SCTL_RAMBOOT_CONFIG` (default `/etc/sctl/ramboot.conf`), keeps the payloads in `/tmp/sctl/cache/{sctl-server,sctl-comms,musl-libc,libgcc}.payload` and trusts a cached one by its SHA-256 only. From `6af8aa1` on it also starts `/etc/init.d/netage-wanpref` when that exists.
- `/etc/sctl/ramboot.conf`: `install.sh`'s keys (`RUN_DIR`, `CACHE_DIR`, `BIN`, `PLUGIN`, `MUSL_LIBC`, `LIBGCC`, `SCTL_CONFIG`, a URL, SHA-256 and gzip flag for each of the four payloads, `MIN_TMP_KB`, `FETCH_TIMEOUT_SECS`, `CONNECT_TIMEOUT_SECS`, `FETCH_ATTEMPTS`, `FETCH_RETRY_SECS`, `ALLOW_UNSIGNED`). On Bus 01 `FETCH_ATTEMPTS=60`, and the URLs name the relay by IP (`http://174.138.114.209:8081/...`: the bus's resolver timed out on the name).
- `/etc/sctl/sctl.toml`: the unit's key and serial, `[comms]` and `[lte]`, the `[tunnel]` block (on Bus 01 written by hand); on Bus 01 also `state_dir = "/etc/sctl/state"`, which holds the Infra targets and credentials. 0.6.2 tolerates unknown keys, so a key it ignores (`relay_route`) may sit there and take effect under a newer agent.
- No `/etc/sctl/install.json`.
- In RAM: the four cached payloads, the expanded `/tmp/sctl/sctl-server` and `/tmp/sctl/lib/{libc.so,libgcc_s.so.1,libsctl_comms_quectel.so}`; the agent runs as `/tmp/sctl/lib/libc.so --library-path /tmp/sctl/lib /tmp/sctl/sctl-server serve`.
- `netage-wanpref`: installed, enabled at boot and started by every `install.sh` from 2026-08-10 on; absent on a unit installed with the bring-up's files.
- BusyBox on uClibc: no `sha256sum` (`openssl dgst -sha256` is used), no `setsid`, `start-stop-daemon` present, `curl` present, `du` present (`install.sh` uses it).

What the current install writes beyond that: today's `ramboot.sh` (the cache gate; it starts `netage-wanpref` when that init exists), `install.json` (`{"v":1,"layout":"ramboot","target":"mips_24kc","helper_prefix":["/tmp/sctl/lib/libc.so","--library-path","/tmp/sctl/lib"]}`), and a `ramboot.conf` naming the release's files on the relay's mirror.

## 3. Deliverables

- `devices/we826-qwd/ramboot-refresh.sh <version> [wait_secs] [premove_secs]`, BusyBox ash and uClibc safe, run detached from its stage, reporting one word in `<stage>/state` (`started`, `fetching`, `installing`, `trial`, `promoting`, `restarting`, `rolling_back`, `rebooting`, then `done`, `rolled_back`, `failed` or `needs_hands`) and logging to `/tmp/sctl-we826-refresh.log`:
  1. checks every staged file against `files.sha256` (no `sh -n`: the bytes are proven, and an old ash may run what `-n` should only parse);
  2. recognises the layout of section 2 or refuses (`failed`, nothing touched, no fetch): the shared ramboot init, a `ramboot.conf` naming the four payloads with every path the one the current layout uses, `sctl.toml`, no `install.json` (or a `ramboot`/`mips_24kc` one without `helper_prefix`), no `/etc/sctl/disabled`, the musl loader in `/tmp/sctl/lib`, and the running agent answering `/api/health` with its version. It also refuses: a tunnel in `sctl.toml` (any `[tunnel]` header form) that is down in the old agent's health, or a tunnel up that `sctl.toml` does not name (healthy then means the tunnel, exactly when the old agent had it); new URLs by name when the old `SERVER_URL` names the mirror by IP; `relay_route` other than `off` unless the old agent's health reports the route as its own; `netage-wanpref` installed but not running, or running but not enabled at boot (today's `ramboot.sh` would start it); a state dir larger than 2 MB. It logs which released init and `ramboot.sh` it found;
  3. keeps `/tmp` free at least the old `MIN_TMP_KB` (24 MB) at every step while the old agent runs, since an old `ramboot.sh` checks it at every respawn: before fetching, for the new payloads (their sizes are staged) and the larger of the probe (estimated by the old expanded files) and the old payloads; before the probe, for its measured expanded size; before the old payloads, for their size. 64 KB plus the state dir on the overlay;
  4. fetches the four new payloads into a work directory and verifies each SHA-256; runs the new server through the new loader: `--version` must print the version, `target` must print `mips_24kc`, and `install-info --config /etc/sctl/sctl.toml` with `SCTL_INSTALL_JSON` on the staged file must parse both and report `ramboot` with the loader prefix; fetches the four old payloads from the old URLs and verifies them against the old `ramboot.conf` (proving that a cold boot of the old layout can still fetch them; refused otherwise), keeping them in RAM. No fetch starts or runs past `premove_secs` (1800 s) from the launch;
  5. copies the init, `ramboot.sh`, `ramboot.conf`, `sctl.toml`, `install.json` (when present) and the state dir to `/tmp/sctl-we826-refresh-rollback` with their SHA-256s;
  6. stops the old agent with the init that started it and makes sure it is gone: the supervisor within 2 s and the daemon within 10 s (then SIGKILL), only pids whose `/proc/<pid>/cmdline` is sctl's, any daemon started meanwhile, then `/api/health` silent. If that fails, the RAM copies are dropped, the init starts the old agent again, and the run ends `failed`. Writes `ramboot.sh` and the init (renamed whole, synced; both start the old version from the old `ramboot.conf`); moves the new payloads into the cache;
  7. trial: starts the new init with `SCTL_RAMBOOT_CONFIG` on a copy of the new `ramboot.conf` in `/tmp/sctl`, so flash still boots the old version. Healthy is `/api/health` answering the version and, when the tunnel is required, connected with the same `reconnects` for 60 s (at least two looks, 5 s apart), the window starting within `wait_secs` (300 s); a bad look or a reconnect starts it again;
  8. promotion: `ramboot.conf`, then `install.json`, each renamed whole and synced;
  9. restarts once more without `SCTL_RAMBOOT_CONFIG` (the supervisor would keep it, and the first managed upgrade's restart would boot the RAM copy) and requires the same health from flash, with layout `ramboot`;
  10. otherwise (7, 8 or 9): puts `install.json` and `ramboot.conf` back first and syncs, stops the new agent with the new init, puts back the init, `ramboot.sh`, `sctl.toml`, the state dir and the old payloads in the cache, checks each against its recorded SHA-256, starts the old init and waits for the old version with its tunnel (when it had one); if it does not come, restarts it and waits again: `rolled_back`, or `needs_hands` when the restore was incomplete. When the restore of the boot files is complete and the old agent still has not come back, `rebooting`: the unit reboots into the restored layout, which fetches what step 4 proved is served.
  `sctl.toml` is never written. The new `ramboot.conf` keeps the unit's `MIN_TMP_KB`, `FETCH_*` and `CONNECT_TIMEOUT_SECS`, and the log names any old key it does not carry. `REFRESH_*` variables exist for the tests only (fakes, timings, checkpoints and injected faults).
- `devices/we826-qwd/refresh-stage.sh <release.json> <mirror base> <out dir>`: writes the stage (the current init and `ramboot.sh`, the `ramboot.conf` for the release's four `mips_24kc` files on that mirror, `install.json`, `sizes` from the manifest, the script, `files.sha256`) from a manifest already verified.
- `rundev.sh device upgrade-remote <name> <version> <user@relay | mirror URL>`: the layout probe answers `we826` (ramboot through the musl loader, no `install.json` naming it) and `we826-managed` (refused: a rollout citizen); every other answer is unchanged. The WE826 path reads the version's `release.json` and its signature from the mirror (from the relay's listing when given `user@relay`), checks the signature against the keys the agent embeds (`server/src/upgrade/keys.rs`; `SCTL_TRUST_KEY` adds a bench key) and names the key by its id, checks the version and that the mirror serves the four payloads with the manifest's SHA-256s, refuses a unit whose health reports another target or a layout other than `ramboot`, refuses a mirror by name for a unit whose `SERVER_URL` is by IP (printing the by-IP command), stages the files through the file API, launches the script in its own session (`start-stop-daemon -b`, else `setsid`, else a background job; never with a signal ignored) with `WE826_WAIT_SECS` and `WE826_PREMOVE_SECS`, follows the state file (`WE826_WATCH_SECS`, by default longer than the device can take), reports a stage gone from `/tmp` as a reboot, prints the log tail on `failed`, `rolled_back` and `needs_hands`, says on a watch timeout whether anything has moved yet, and after `done` checks that health reports the version, layout `ramboot` and target `mips_24kc`.
- Tests: `devices/we826-qwd/tests/ramboot-refresh-test.sh` and `upgrade-remote-test.sh` (section 5).
- `docs/upgrade.md` (the `ramboot` row, "A WE826 installed before 0.6.9", "By hand"), `docs/releasing.md`, `devices/we826-qwd/README.md`, `CHANGELOG.md` `[Unreleased]` (CRLF), this TRD and its index rows.

## 4. Decisions inside the move

- **Flash switches only after the new version proved itself from RAM.** The first start of the new version reads a RAM copy of its `ramboot.conf` (`SCTL_RAMBOOT_CONFIG`), so a power cut during the trial, or during a rollback that has put `ramboot.conf` back, boots the old version. Only then are `ramboot.conf` and `install.json` written, and the version starts again from flash. The init and `ramboot.sh` go first: today's start the old version from the old `ramboot.conf`, and the old ones the new (the mixes were checked). Every flash state the move passes through boots one version whole, and none is the old version with an `install.json` that names the loader (which no later move or rollout could fix).
- **A rollback needs no network; a reboot needs only what was proven.** The old payloads are fetched from their URLs before anything moves (a cold boot of the old layout would fetch exactly those), verified, and kept in RAM until the move is settled, then put back in the cache before the old init starts. The bus is mobile: the moment the new agent fails may be the moment its link goes too. ADR-002 section 5 rejects keeping two payload sets in the steady state; this copy lives only during the move and is removed at `done` (the small files stay in `/tmp` until the next boot).
- **Healthy means steady, and the tunnel is judged by what the unit had.** The requirement comes from the old agent's live health and `sctl.toml` together, and a disagreement is refused rather than guessed: a header the script misreads must not turn "healthy" into "the version answers". A tunnel that registers and is then kicked shows as a reconnect and restarts the 60 s window.
- **Stop with the init that started it, start with the init that will own it.** A `restart` through the new init would kill the old agent correctly, but a rollback's restart through a single-shot old init would leave the new init's supervisor running, and it would respawn the new version. The supervisor is killed within 2 s, before its 10 s respawn, and only pids whose command line is sctl's are signalled.
- **No signal is ignored, by the script or its launcher.** The init's supervisor is a shell started from the script; a signal ignored there is inherited, ash cannot trap a signal ignored on entry, and `stop` (TERM) would no longer stop sctl; the agent's sessions would inherit an ignored HUP too. The script catches HUP and TERM with a handler (reset to the default in anything it execs) and is detached in its own session, so the agent's exit cannot take it down. (On the RUT241, procd starts the service, so its launcher's `trap "" HUP TERM` is harmless there.)
- **The move changes the agent and its files, nothing else on the unit.** The trial's side effects that would outlive a rollback are refused up front: `relay_route` (a 0.6.2 agent ignores it, a current one takes the relay's route and leaves it in place when it exits) and a `netage-wanpref` that today's `ramboot.sh` would start. The state dir, where the new agent writes, is restored with the files.
- **The new binary reads this unit's configuration before anything moves.** `install-info` parses `sctl.toml` and `install.json` with the new version's types; `validate()` runs only at `serve`, so a configuration the new agent parses but refuses to serve is caught by the trial and rolled back.
- **A deadline before the move, none after it.** Nothing stops the old agent once `premove_secs` have passed (a slow LTE fetch ends `failed`, nothing moved); from the stop on, the script runs to an outcome, bounded by its health windows.
- **An unfinished move blocks the next one.** `/tmp/sctl-we826-refresh-rollback/in-flight` exists from the stop to the outcome (and stays after an incomplete restore): a later run refuses rather than replace that backup.
- **Not built:** a separate dead-man process. The script is detached in its own session and shares nothing with the agent it stops; what it does not survive (a power cut) boots a whole version, by IP. A soak after `done` is the managed path's job for later releases.
