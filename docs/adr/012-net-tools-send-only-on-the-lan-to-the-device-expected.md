# ADR-012: Net tools send only on the LAN, to the device expected

Status: Accepted (2026-10-21). Realized by [TRD-9](../trd/TRD-9-release-0-6-12.md) (release 0.6.12). Builds on ADR-006 and puts its decision 1 for the SNMP community into the code. Cites `docs/http-api.md` (`POST /api/infra/discover`, `GET /api/infra/discover/subnets`) and `docs/config.md` (`[lte] interface`, the environment variables). Lines are at sctl `ece8b45`.

## 1. Trigger

- **A restart that left by the LTE (2026-10-16).** A site's router went silent, and the unit watching that site lost its address on the site's network and ran on LTE. Later that day a person asked the fleet for a whole-bar restart of the site's power bar, and the unit ran `sctl net snmp set <bar> <oid> i <n> -v 1 -c "${SCTL_CRED_PASS_1}"`. Its only route to the bar's private address was the LTE default route, so the set left over the carrier's network with the community in clear. Nothing answered: the tool said "no answer from the SNMP agent", and the fleet showed only "exit 1". The first attempt by hand to reach the site's devices that day used a temporary /32 address on the unit's wired port plus a host route to each device, not a connected /24.
- **Another device at the address (2026-10-16 and 2026-10-18).** On 2026-10-16 the router's monitored target read up while a switch answered at the router's address. After an address shuffle on 2026-10-18, a scan found another device at a target's address, and the fleet wrote that device's MAC into the target's record; the target then read up for two days from the wrong device. Checks and commands trust the address, so a command reaches whatever answers there. The same site has a router that answers at two addresses with one locally administered MAC: a MAC can be generated, changed or shared.
- **Scans spend the LTE.** A scan nobody chose subnets for sweeps every network the unit holds, its LTE and the fleet mesh included. It reads MACs before its sweep, so a host that nmap or the ping fallback finds first comes back without one. Nothing marks the unit's own addresses, and its former addresses became monitored targets.

## 2. What existed

Code paths are under `server/src/`; `devices/`, `mcp/`, `CHANGELOG.md` and the `snmp2` crate are named as such.

**The net tools (0.6.11, ADR-006).**

- `sctl net` is a one-shot process (`main.rs:126-128, 312-315`). Only `sctl net http` loads a configuration, for its TLS pin store: its undocumented `--config <path>` (`net_tools/mod.rs:218, 249`), else `./sctl.toml` in the working directory (`/tmp` on the unit templates, each model's `sctl.toml.template:22`), else compiled defaults (`config.rs:846-873`). `Config::load` panics on a file it cannot read or parse (`:851-855`). Nothing passes the agent's path down, so no tool knows `[lte] interface`.
- Exit codes are 0 (done), 1 (failed; the JSON says why) and 2 (usage) (`net_tools/mod.rs:9-11`). Secrets are to come from the environment "expanded by the shell" (`:11-13`), but a variable expanded in an argument is in the tool's argv.
- **SNMP.** `-c` or `--community` (`net_tools/mod.rs:91`) wins over `SCTL_SNMP_COMMUNITY`, which counts only when not empty; with neither, get and walk send `public` and set is a usage error (`:279-286`). The output never carries the community (`:312-321`). The fleet stores `-c "{{password:<target>}}"`, which reaches the unit as `-c "${SCTL_CRED_PASS_1}"` with the value in the command's environment (fleet ADR-0017), so the expanded community is in argv, readable by every local process while the tool runs; the activity log keeps the command unexpanded (`routes/exec.rs:386`). `SCTL_SNMP_COMMUNITY="${SCTL_CRED_PASS_1}" sctl net snmp ...` already works. ADR-006 decision 1 said "never the command line"; TRD-6 (section 2) and the 0.6.11 changelog (`CHANGELOG.md:19`) recorded "`-c` or `SCTL_SNMP_COMMUNITY`", which is what shipped.
- `snmp::Target` has no interface (`net_tools/snmp.rs:20-27`). `session()` (`:150-158`) opens an `snmp2` 0.5.2 session, which binds its own UDP socket to the unspecified address (`snmp2` `src/asyncsession.rs:69-110`). No constructor takes a caller's socket, and the request builders and the answer's checks (`Pdu::validate`) are crate-private (`snmp2` `src/pdu.rs:311-506, 654`); the decoder, `Pdu::from_bytes`, is public (`:567`). A v1 or v2c request carries the community in clear (`net_tools/snmp.rs:327-347`).
- **TCP.** `--timeout` is the only option; the first other token is the host, the second the port, the rest is ignored (`net_tools/mod.rs:127-145`). So `sctl net tcp <host> <port> --dev X --expect-mac Y` runs unguarded on 0.6.11 and can exit 0. `probe` connects by the kernel's route, unbound (`net_tools/tcp.rs:16-35`).
- **HTTP.** An unknown option is a usage error (`net_tools/mod.rs:219-221`). Basic auth is `-u user:password`, and the help suggests `"$SCTL_CRED_USER_1:$SCTL_CRED_PASS_1"` (`:25, 194`): argv again. Redirects are followed to any host (`net_tools/http.rs:150-175, 213-226`), and every hop adds the caller's headers and Basic auth (`:189-193`). A 307 or 308 keeps the method and the body; only a 303, and a 301 or 302 after a POST, go on as a GET without one (`:217-221`). Each hop is one `routes::fetch::execute` (`:208`), which connects unbound (`routes/fetch.rs:529`) and also serves `POST /api/fetch` (`:490-499`) and the Peplink check (`infra/profiles/peplink.rs:212, 243`).
- **Checks that send a secret.** The Infra SNMP check reuses `net_tools::snmp`: a v2c GET of sysDescr with the pushed community, `public` by default, every interval, by whatever route the kernel picks (`infra/checks.rs:110-114, 411-466`). A community refused as invalid is quoted in the check's detail (`:150-163`). The Peplink check logs in with a stored username and password through `execute` (`infra/profiles/peplink.rs:43-62, 198-206`).

**What the agent knows about its interfaces.**

- `netwatch` reads the main table only and keeps one address per interface (`netwatch/mod.rs:164-168, 197-204`); its netlink layer reads every IPv4 address with its prefix and secondary flag, and every link's flags (`netwatch/netlink.rs:293-359`).
- `source::route_get` asks the kernel for the route to a destination, as `ip route get` does, sending nothing to it (`netwatch/source.rs:45-82`). It sends the destination alone (`:62-68`) and returns the interface, next hop and source, not the route's type, so a local, broadcast or multicast destination looks like a unicast one. `source::bind_to_device` sets `SO_BINDTODEVICE`; a source address alone only picks the source (`:145-170`). Before kernel 5.7 the bind needs `CAP_NET_RAW` (`netwatch/owner.rs:2547-2549`); the init scripts start the agent as root.
- No interface has a role: an uplink is any interface with a default route (`netwatch/owner.rs:9-14`), and names stand in. Discovery skips `lo`, `docker`, `veth` and `tun` and keeps `wwan*` and `wg*` on purpose (`infra/discovery.rs:317-322, 338`); its candidate LAN interfaces skip `wg` and `wwan` (`:549-582`); the mesh is the constant `wg0` (`tunnel/net_state.rs:65`).
- The LTE netdev is `[lte] interface`, `wwan0` by default (`config.rs:420-438, 506-508`): `wwan0` on the XE300, whose modem is framed like Ethernet (802.3 mode, `devices/xe300/README.md:195-200`), `qmimux0` on the RUT241 (`devices/rut241/README.md:62-63`), `usb0` on the WE826 (`devices/we826-qwd/README.md:34`). `[lte]` is optional and needs `[comms]` (`config.rs:85, 831-836`), so the relay's configuration (`server/relay.toml.example`) names none. The XE300's WAN port `eth1` is wired like its LAN's `eth0` (`devices/xe300/README.md:17`); on a probe, the site's network is there.
- The only neighbour-table reader is discovery's shell `ip neigh show` (`infra/discovery.rs:755-783`).
- The MCP server reads `SCTL_CONFIG` as the path of its JSON devices file (`mcp/src/config.rs:6, 60`; `mcp/README.md:123`). The ramboot wrapper's `SCTL_CONFIG` is a shell variable it does not export (`devices/common/sctl-ramboot.sh:26, 236`).

**Discovery.**

- With no subnets in the request, a scan sweeps every subnet `auto_detect_subnets` returns (`infra/discovery.rs:46-56`), though its comment says it reads the ARP table only (`:38-41`): every IPv4 network of every interface but `lo`, `docker`, `veth`, `tun` and 127/8, the LTE and the mesh included (`:317-373`); a /24 guessed around each default route's gateway, unless a network the same interface holds an address on contains the gateway (`:375-397, 474-530`); and what a 5 s passive sniff heard (`:399-424`). The same list answers `GET /api/infra/discover/subnets` and the tunnel's `tunnel.infra.discover.subnets` (`infra/routes.rs:304-316`; `tunnel/client.rs:4415-4431`).
- Phase 1 reads the neighbour table before the sweep, every state but FAILED, without the interface (`infra/discovery.rs:100-117, 755-783`). Phase 2 tries `nmap -sn` (addresses only, `:803-822`); when it finds nothing, `arp-scan --arpspa=0.0.0.0` (with MACs) on a subnet the unit has no address on, or on each candidate LAN interface for one the detection does not know (`:824-858`); when that finds nothing, a ping fallback. nmap and the ping fallback send by the kernel's route, unbound, to whatever subnet the request names. A MAC from the sweep is kept only when Phase 1 gave none (`:125-133`): an older entry wins over a fresh answer.
- The ping fallback pings `.1` to `.254` of the network's first three octets, whatever the prefix (`:860-902`), and runs the whole detection again, sniff included, to find each subnet's interface (`:532-541, 832`).
- Phase 3 connects to ten TCP ports on every address found, unbound, with a 2 s timeout (`:148-160, 904-947`). Phase 4 asks the unit's resolver for each name (`:163-169, 949-971`). Nothing in a found device says it is the unit itself (`:20-28`).

**The fleet in the meantime.** With fleet TRD-35 (slices 1, 3 and 8 implemented 2026-10-21), a scan no longer rewrites a target's MAC, and the fleet names a scan's subnets itself (given, else saved, else its pick of the unit's LAN networks), so a saved subnet the unit has lost its address on is still named. After a scan the fleet fills missing MACs from every complete entry of `/proc/net/arp` (`src/lib/modules/devices/domain/infra-scan-facts.ts` (fleet)); the kernel marks STALE, DELAY and PROBE entries complete too. Slice 8 warns, without refusing, when the unit holds no address on a power target's network and the command brings none (`src/lib/modules/devices/domain/power-reach.ts` (fleet)), since a site's recovery runbook adds its own temporary address.

## 3. Decision

**The net tools.**

1. **On the LAN by default.** Before sending anything, `sctl net snmp`, `http` and `tcp` ask the kernel for the route to the destination (`source::route_get`, which TRD-9 extends to return the route's type). They send only when it is a unicast route with no gateway that leaves by a LAN-side interface (decision 2) holding an IPv4 address; otherwise they refuse with `not_on_lan`, or `no_address` when that interface holds none (decision 5). The test is the kernel's route, not "inside a connected prefix": a /32 address plus a host route passes, as on 2026-10-16, and so does a route a runbook adds one step earlier. The guard runs in the tool's process as it sends.
   - A destination the unit holds itself (its own addresses, loopback) passes: nothing leaves the unit.
   - A broadcast or multicast destination is refused (`not_unicast`): the tools speak to one device.
   - A destination behind a gateway is refused, even a gateway on the LAN side: the tool cannot see past it, and a MAC check would see the gateway's MAC.
   - A host name is resolved once; the guard judges its first IPv4 address, and the tool connects to that address only (HTTP keeps the name for `Host` and TLS). The lookup carries a name, never a secret.
   - An IPv6 destination is refused (`ipv6`) until a decision covers it: the agent reads IPv4 networks only.
   - A tool that cannot read the routes or bind refuses (`guard_failed`). It never sends unguarded.
2. **The LAN side.** An interface is on the LAN side when it is up, not loopback, takes ARP, is not point-to-point, and is not the LTE netdev. The flag test (`IFF_NOARP` and `IFF_POINTOPOINT` clear) leaves out WireGuard, tun, PPP and a raw-IP modem, but not a modem framed like Ethernet, as on the XE300; hence the LTE netdev is named. A wired WAN port is on the LAN side: on a probe, the site's network is there. The tool reads every address with its prefix, secondary ones included, and each link's flags over netlink.
   - The LTE netdev is the agent's `[lte] interface`. A tool reads the agent's configuration from `--config <path>`, now documented and taken by all three tools, else from `SCTL_AGENT_CONFIG`, which the agent sets to the absolute path of the file it loaded, in the environment of every command a caller or a pushed config gives it to run: exec, sessions and their jobs, Infra checks and recoveries. It never reads `./sctl.toml` from its working directory (`/tmp` on the units, writable by any local process), where a planted file could name another LTE netdev.
   - A configuration that cannot be read or parsed is a refusal (`config_unreadable`) naming the path and quoting nothing from the file: never a panic, never a quiet fall back to defaults.
   - With no configuration, one without `[lte]`, or one whose `[lte] interface` the unit lacks, an interface named like a supported model's modem bearer (`wwan*`, `qmimux*`, `usb*`) counts as LTE, and the answer says the name decided it.
   - Each interface's role (`lan`, `lte`, or `tunnel` for a point-to-point or no-ARP link) appears in refusals and in the discovery subnet list.
3. **Bound to the interface the guard approved.** The tool binds its socket to that interface (`SO_BINDTODEVICE`) and to the source address the route gives before sending. A lease that ends, or an address a runbook's timer removes, between the check and the send makes the send fail rather than move. Nor can mwan3 move it: mwan3 marks the unit's own traffic so that the kernel routes it again after the check, and a bound socket keeps its interface through that (section 6).
   - `--dev <interface>` names the interface instead of the kernel's choice. It must be on the LAN side and hold an address (a bridge port is named by its bridge), and the destination must lie under a main-table route through it with no gateway: its own network, or a host or network route a runbook added (`not_on_lan`, `no_address`). This is judged from the routes, never from a lookup tied to the interface: with no route through it, the kernel answers such a lookup, and routes a socket bound to it, as if any address were on the link, an internet address or a typo included (`net/ipv4/route.c`). A runbook that adds a temporary address passes `--dev`.
   - SNMP goes out from a bound socket too. TRD-9 chose between an `snmp2` that takes the caller's socket (upstream or patched) and the agent's own encoder for its three requests, decoded by `snmp2` and checked for request id, community and type: it takes the agent's own encoder (TRD-9 section 4).
4. **`--expect-mac <mac>`: the device expected, or nothing sent.** After the route check and before any payload, the tool sends one ARP request for the destination on the bound interface and waits briefly, within its timeout. It sends only when every answer names the expected MAC, and so does the kernel's neighbour entry for the address if it holds one. Another MAC, or two MACs, is `mac_mismatch`; no answer is `no_answer`.
   - The neighbour table alone is not enough: right after a shuffle a STALE entry still names the device that held the address, and the kernel sends to it until it probes again.
   - The check proves that the device answering holds that MAC, no more: a generated or shared MAC passes for whichever device holds it, one device at two addresses passes at both, and a record that took another device's MAC, as on 2026-10-18, lets that device through. Keeping the record right is the fleet's (fleet TRD-35 slice 3; fleet ADR-0039).
   - Without a packet socket the tool refuses (`guard_failed`); it never skips the check. With the flag, a destination the unit holds itself is refused (`own_address`). A MAC is written with colons or hyphens, in either case; anything else is a usage error.
5. **A refusal says why, and that the request was not sent.** A refused request exits 3, a new code; 0, 1 and 2 keep their meanings. Exit 3 means the request never left: at most a name lookup and decision 4's ARP request did. The JSON carries `ok: false`, `refused` (one of `not_on_lan`, `no_address`, `not_unicast`, `ipv6`, `own_address`, `mac_mismatch`, `no_answer`, `config_unreadable`, `guard_failed`), a one-line `reason`, `host` (the address judged), the route the kernel would have used (interface, role, gateway), the unit's LAN-side networks by interface and, after an ARP request, the MACs that answered. It never carries a secret, and no usage error repeats an option's value. In documentation addresses, the 2026-10-16 set would have read: `198.51.100.50 is not on a network this unit holds on its LAN side: the kernel would send it by wwan0 (lte) through a gateway. LAN side: br-lan 192.0.2.1/24; eth1 holds no address.` How long the unit has been without an address is the fleet's to say, from the history it keeps.
6. **HTTP keeps its credentials with the device it was sent to.** Every hop of a redirect passes decisions 1 to 4 on its own, `--dev` included. A redirect to another scheme, host or port drops the Basic credentials, every header the caller set and the body, and is not followed when it would resend a body (a 307 or 308 after a request with one), nor, with `--expect-mac`, to another address. A redirect not followed, for these reasons or because its hop is refused, ends the request: the answer is that redirect (status, `Location`) with `not_followed` and the reason, exit 1, since the first request was sent.
7. **The SNMP community comes from `SCTL_SNMP_COMMUNITY` only.** `-c` and `--community` are a usage error (exit 2) whose message shows the environment form, `SCTL_SNMP_COMMUNITY="${SCTL_CRED_PASS_1}" sctl net snmp ...`, without the value; the shell then puts the value in the tool's environment and in no argv. A variable set but empty, which is what a reference to a credential the command does not carry expands to, is a usage error too, never `public`. Unset, `public` stays the default for get and walk, and set still needs a community. This is ADR-006 decision 1, now in the code. The Infra SNMP check's detail never quotes a community.
8. **No stray arguments.** `sctl net tcp` refuses an argument it does not know, as `snmp` and `http` already do.
9. **What the guard covers.** The three tools, and the two Infra checks that send a stored secret: the SNMP check (its community, every interval) and the Peplink check (its login). Off the LAN, such a check reads down with the guard's reason. `POST /api/fetch` and the checks that send no secret (ping, HTTP through curl, TCP) keep today's behaviour. Whether a check also proves its device's MAC is left to section 7.

**Discovery.**

10. **A scan sends only on the LAN side.** With no subnets in the request, it sweeps the networks the unit holds an address on, on LAN-side interfaces. `GET /api/infra/discover/subnets` gives every subnet its `role`; a /24 guessed from a default route and a subnet the sniff heard are swept only when a request names them. Whatever the request names, every send follows decision 1: nmap and the ping fallback sweep a subnet only when it lies wholly under a no-gateway route through a LAN-side interface, and only on that interface; arp-scan, which stays on the link, runs only on LAN-side interfaces, so a saved subnet the unit has lost its address on is searched by ARP alone; the port probe judges each host by decision 1 and binds to the interface it approved. An LTE or tunnel network, or one behind a gateway, is never swept. The answer's `not_swept` names each subnet the scan did not sweep and why (`not_on_lan`, or `too_large`, decision 13). Phase 1 keeps the LAN side's neighbours only. The comment at `infra/discovery.rs:38-41` and `docs/http-api.md` say what the default is.
11. **A scan reports only MACs it saw.** A host's MAC is one seen answering at its address during the scan: an ARP answer the sweep received (arp-scan's, or nmap's report of one), or the kernel's neighbour entry for the host on the interface that reaches it, read after the sweep and the port probe and REACHABLE then (or permanent, set by hand). For a host still without one, the agent sends decision 4's ARP request and takes the answer: one MAC, else none.
    - The port probe's connects make the kernel resolve every address found, so a host the sweep found first gets its MAC.
    - A STALE, DELAY or PROBE entry may name the device that held the address before a shuffle, so it is never reported. A host the unit already knew often holds one at the read: the probe's first packet turns STALE into DELAY for about 5 s (`delay_first_probe_time`), longer than its 2 s connects. The ARP request settles it.
    - The sweep's answer no longer gives way to an older entry, and an address two MACs answered for gets none.
12. **The unit marks itself.** A host at an address the unit holds now, or with one of the unit's own MACs, carries `own` with the name of its interface. The ping fallback skips the unit's addresses. Remembering former addresses is the fleet's (fleet ADR-0039).
13. **The ping fallback honours the prefix.** It pings the hosts of the subnet's own prefix, without the network and broadcast addresses (a /31 and a /32 have none) and the unit's own, and never more than the 254 addresses it pings today. A larger subnet is swept only by nmap or arp-scan, else is `not_swept` as `too_large`. Each subnet's interface is found once per scan, without a second sniff.

## 4. Consequences

- The 2026-10-16 restart would have stopped on the unit with exit 3 and decision 5's reason; the community would never have left the unit.
- A runbook that brings its own address keeps working when it brings the route too: an address with the network's prefix, or a /32 plus a host route, as on 2026-10-16. With `--dev`, an address removed early makes the send fail. Only the agent sees the routes as it sends, so on 0.6.12 its answer is the one that counts; the fleet's warning (fleet TRD-35 slice 8) is for 0.6.11 units.
- The guard keeps a request on a link the unit holds. It cannot tell a site's LAN from a carrier's segment on a wired port (a modem in bridge mode) or a Wi-Fi client uplink: all read `lan`.
- A command that reaches a device behind a gateway, or the internet, stops working through the net tools. None is known (section 7). A test of the site's internet is a `ping` bound to an interface, as the fleet's site diagnose runs it.
- The community leaves argv, which every local process can read, and goes nowhere new: the tool's environment already holds it as `SCTL_CRED_PASS_n`, readable only by root and the same user, and fleet TRD-35 slice 1 and ADR-011 refuse reading a process's environment.
- Before any unit runs 0.6.12, the fleet:
  - rewrites every stored SNMP command (power actions, recoveries, runbooks) to the environment form, which 0.6.11 already runs, and gets it onto the units: each unit's Infra configuration pushed again, each runbook kept on a unit written again. Otherwise a recovery the unit stores with `-c` exits 2 until its next push. Fleet ADR-0040's one-time rewrite carries the commands the fleet stores; a runbook kept on a unit is written again by a person's save through the fleet, since that rewrite writes none, or its unit is held (TRD-9 section 5);
  - sends `--dev` and `--expect-mac` only to 0.6.12 or later, before the positional arguments: on 0.6.11 a leading flag is a usage error in all three tools, while `tcp` ignores a trailing one, so a 0.6.11 `tcp` success is never read as a checked MAC;
  - reads exit 3, with `refused` in the tool's JSON, as "not sent" only when the command is the tool alone; only then can an audit row state it as a fact.
- From 0.6.12 the fleet stops its own neighbour read after a scan, which would put back the MAC decision 11 withholds, and a restart's MAC check moves from the fleet (fleet ADR-0040) to `--expect-mac`.
- An SNMP or Peplink check whose target the unit does not reach on the link reads down from 0.6.12 (section 7).
- A scan spends no LTE on its sweep and port probe, whatever subnets it names, and touches no mesh (Phase 4's lookups aside, section 7). Its answer gains `own`, the subnet roles and `not_swept`, documented in `docs/http-api.md`; older readers ignore them.
- No configuration field is added; `docs/config.md` names `SCTL_AGENT_CONFIG`. Once `sctl net http` reads the agent's configuration, it keeps its TLS pins in the agent's state directory, and a pin recorded under the default directory is asked for again.
- `sctl help net` gains `--dev`, `--expect-mac`, `--config`, exit 3 and the `refused` codes, and loses `-c`. The binary grows by the guard, the ARP request and a small SNMP encoder, in the one 0.6.12 release that also carries ADR-010 and ADR-011. What a unit downloads depends on its target (TRD-9 section 5): about 3.9 MB of gzipped payloads for a `mips_24kc` unit (the XE300, the WE826), plus 1.3 MB of loader libraries on a WE826 when they change, and about 7.4 MB of raw binaries for a `riscv64` unit. The other targets are measured with the release.

## 5. Rejected alternatives

- **"Inside a connected prefix" as the test.** It refuses the /32 address plus host routes that reached the site's devices by hand on 2026-10-16.
- **`--dev` as "on this link, whatever the tables say".** The unit would ARP on the site's port for an internet address or a typo, and a proxy-ARP router could carry it on.
- **Checking without binding.** An address can go between the check and the send, and mwan3 routes a marked packet again after it; a source address alone does not pin the interface (`netwatch/source.rs:145-149`).
- **`--expect-mac` from the neighbour table alone.** A STALE entry outlives a shuffle; only an answer now says who holds the address.
- **A flag that turns the guard off.** One word, carried by any copied command, would bring back 0.6.11. The tools exist for LAN gear (ADR-006 section 1; `net_tools/http.rs:1-4`).
- **The guard in the fleet only.** The fleet cannot see a route a runbook adds one step earlier, nor the moment of sending.
- **Roles from interface names alone.** A name can be a modem on one model and a wired adapter on another.
- **A configuration list of LAN interfaces.** Every install script would have to write it right; the kernel already says which interfaces take ARP.
- **`SCTL_CONFIG` for the path.** A staff shell set up for the MCP server would hand the tools its JSON devices file.
- **Passing values, not a path** (`SCTL_STATE_DIR` and the LTE netdev). `SCTL_STATE_DIR` in every child's environment would also override the state directory of an agent started from one, since the environment wins over the file (`config.rs:875-890`).
- **Keeping `-c` beside the environment.** A copied command would keep the community in argv. One way in is one a reviewer can check, and 0.6.11 already accepts it.
- **Addresses only, no host names.** The lookup carries a name, never a secret, and its address is judged like any other.

## 6. What TRD-9 proves

Before the release:

- A network-namespace rehearsal, run as root and ignored by default like `server/tests/relay_route_netns.rs`, with a LAN veth and an "LTE" veth that holds the default route:
  - an SNMP set off the LAN exits 3, and a capture on both veths sees nothing;
  - a /32 address plus a host route passes and leaves by the LAN veth; with `--dev`, an address removed mid-run never sends by the LTE veth, and an address under no route through the named veth exits 3 with nothing on the wire, ARP included;
  - fwmark rules and a policy table that steer the unit's traffic to the LTE veth, as mwan3 does, do not move a bound request, SNMP included;
  - with `--expect-mac`, another MAC, two MACs and no answer each refuse with only the ARP request on the wire; with a STALE entry naming another device, nothing reaches that device: the payload goes to the expected MAC, or nothing is sent;
  - a redirect to another host arrives without `Authorization`, the caller's headers or the body, and a 307 to another host after a POST with `-F` is not followed;
  - the community is in no argv, stdout, stderr, check detail or activity-log line, refusals and the `-c` usage error included; a JSON file given as the configuration is `config_unreadable`;
  - a default scan sweeps no LTE or mesh subnet; a named subnet the unit holds no address on sends nothing by the LTE veth and is `not_swept`; a host the sweep found first, and one whose entry was STALE before the scan, come back with their MACs; the unit's own addresses carry `own`.
- `cargo test`, clippy on the pinned 1.97.1 and `fmt --check`, as CI runs them; CI has no privileged job, so TRD-9 records the rehearsal's run.
- Which units ship `nmap`, `arp-scan` and `tcpdump`, and, on each kernel from 3.3.8 up, whether the neighbour read after the port probe fills the sweep's hosts.

After the release, on the first ring: on an XE300 with mwan3 running, a refused request names `wwan0` as LTE and a `--dev` request on the wired WAN port passes; on each model, a `sctl net` child reads `[lte] interface` through `SCTL_AGENT_CONFIG`.

## 7. Settled questions

Each question this ADR left open, with its answer (2026-10-21): the default it proposed, and for questions 9 to 11 the release's.

1. **Off-LAN uses.** Does any runbook kept on a unit call `sctl net` toward the internet or a device behind a gateway? Settled: before the release, TRD-9 lists every stored command and runbook that calls the tools, with its destination. No exception is kept: from 0.6.12 such a call is refused.
2. **Checks off the link.** An SNMP or Peplink target the unit does not reach on the link reads down from 0.6.12. Settled: TRD-9 lists them first.
3. **The kernel's route, not a connected network.** The request that led here asked for "a connected network of the unit's LAN side"; the guard also passes a host route with no gateway through a LAN-side interface. Settled: as decided. A runbook brings its route with its address.
4. **`--expect-mac` asks the wire.** It refuses when nothing answers, not only when the neighbour table names another MAC. Settled: as decided. When to pass the flag is the fleet's (fleet ADR-0040).
5. **HTTP credentials.** `-u`, `-H Authorization`, `-d` and `-F` still put secrets in argv, and ADR-006 meant the environment for HTTP too. Settled: a later decision, since the fleet's own code writes no `sctl net http` command today. Basic auth would then come from `SCTL_CRED_USER_n` and `SCTL_CRED_PASS_n` by slot.
6. **`public`.** Settled: it stays the default for get and walk.
7. **Reverse lookups.** Phase 4 asks the unit's resolver, which may answer over the LTE; the query carries a LAN address, never a secret. Settled: unchanged here.
8. **A check that proves its device's MAC.** Settled: not in this release. It is decided with the fleet's Infra devices (fleet ADR-0039) and reuses decision 4's ARP request.
9. **A UDP 161 probe in discovery.** Settled: not in this release (fleet ADR-0039).
10. **sctlin passing `{{agent}}` through a runbook.** Settled: not in this release (fleet ADR-0040).
11. **What the release costs a unit.** Settled: each target's own download, as TRD-9 section 5 measures it, not one number for every unit.
