# ADR-011: File reads read what is there, and refuse secrets and devices

Status: Accepted (2026-10-21). Realized by [TRD-9](../trd/TRD-9-release-0-6-12.md) (release 0.6.12). Cites `docs/http-api.md` (`GET /api/files`, `GET /api/files/raw`, `POST /api/stp/download`), `docs/errors.md` (the device catalog, the STP codes), `docs/config.md` (`max_file_size`, `data_dir`, `state_dir`, `journal_enabled`, `max_concurrent_transfers`) and `docs/upgrade.md` (the install layouts, the rollback set).

## 1. Trigger

On 2026-10-20 the fleet's assistant read `/proc/net/arp` on a unit through `GET /api/files`, to see the LAN's neighbour table. The answer was an empty file. The agent reads `st_size` bytes in one `read()`, and procfs reports a size of 0. Until the agent reads the table, the fleet reads it with `cat` through exec (fleet TRD-35).

Reading to end of file is the obvious fix. It would also read much more than the neighbour table:

- An exec child carries the credentials it was given in its environment, and `/proc/<pid>/environ` is that environment.
- `/proc/kmsg` blocks, and takes the kernel's messages from the system log.
- A FIFO blocks its reader. A device file acts when it is opened or read, and some never end.

`/proc/kmsg`, a FIFO and a device file can each hold one of the 32 handlers a unit runs relay messages under, for as long as the read lasts. That can be forever. Two read paths, `GET /api/files/raw` and gawdxfer's download, already read to end of file.

## 2. What existed

Code paths are under `server/src/` unless they say otherwise.

- **One path check, for traversal.** `validate_path` refuses a relative path, a NUL byte and a `..` component (`routes/files.rs:153-176`); gawdxfer's `validate_transfer_path` is a copy (`gawdxfer/manager.rs:1026-1056`). The file routes resolve no link, test no file type but a directory, and refuse no path: `server/src` has no rule for `environ`, `kmsg`, `kcore` or `shadow`, and no FIFO, socket or device test. `SECURITY.md:32` and `server/docs/REVIEW.md:11-13` describe path validation as traversal prevention.
- **`GET /api/files` reads `st_size` bytes in one `read()`** (`read_file`, `routes/files.rs:247-359`): links followed (253), only a directory refused (269-274), no open flags (295), a buffer of the cap (or `limit`) or `st_size` less the offset, whichever is smaller (278, 316-318), one `read()` (319-323), and `truncated` against `st_size` (327). By code reading:
  - A procfs file has size 0, so the buffer is empty and tokio returns without calling `read(2)` (tokio 1.49.0, `Cargo.lock:1610-1612`; its `src/fs/file.rs:607`): the answer is empty. Only this keeps `/proc/<pid>/environ` and `/proc/kmsg` unread on this route.
  - A sysfs file reports 4096 bytes and returns its real content, marked `truncated`.
  - tokio caps one read at 2 MiB (its `src/io/blocking.rs:27`, `src/fs/file.rs:615`), so where `max_file_size` is larger, a regular file over 2 MiB comes back cut and `truncated` with no range asked. The compiled default is 50 MB (`config.rs:540-542`; the module doc says 2 MB, `routes/files.rs:14`). The unit templates set 2 MiB (`devices/xe300/sctl.toml.template:14`, the same line for the RUT241 and the WE826); `sctl.toml.bpi` and `server/relay.toml.example` set none.
  - A FIFO blocks the open until a writer comes, and a character device is opened. A ranged request skips the size refusal (280-287), so where the kernel has `/proc/kcore`, a ranged read returns kernel memory.
- **`GET /api/files/raw` streams to end of file, with no cap** (`download_file`, `routes/files.rs:634-701`): the same checks and open, `Content-Length` from `st_size`, then a `ReaderStream` until `read()` returns 0. By code reading, not run: through the relay the unit collects the body (up to 8 MiB within 55 s, `tunnel/client.rs:2394, 2459-2473`), and the relay rebuilds the response with only `Content-Type` and `Content-Disposition` (`tunnel/relay.rs:771-800`). So a caller with the unit's key gets a procfs file whole, `/proc/<pid>/environ` included. `/proc/kmsg` waits up to 55 s; the read then stays blocked in its thread, holding the descriptor, and takes the next kernel messages when they come.
- **gawdxfer hashes the whole file before it serves a chunk** (`init_download`, `gawdxfer/manager.rs:54-189`): traversal checked (59), links followed (61-68), only a directory refused (70-72), `st_size` against `transfer_max_file_size`, 1 GiB by default (74-85), `max_concurrent_transfers`, 4 by default (87-105), then the hash (110-113). `hash_file` reads 64 KiB blocks until `read()` returns 0, with no byte cap and no deadline (`gawdxfer/hasher.rs:13-25`).
  - A character device has size 0 and passes the size check. `/dev/zero` never ends, and keeps the XE300's MIPS 24Kc busy (`devices/xe300/README.md:10`). A FIFO blocks at the open, `/proc/kmsg` at the read. This is reachable today with the unit's key.
  - A transfer is registered only after its hash (151-154), so the limit counts no running hash: any number can run at once, each holding a tunnel permit.
  - A procfs file is offered as one empty chunk (`compute_chunks`, 1017-1024; `serve_chunk` sizes chunks from `st_size`, 432-436), while `file_hash` covers its real bytes. That download can never verify.
  - `TransferManager` holds its transfers, its config, the progress channel and the activity log (26-50), and nothing of the agent's directories. An STP code that `routes/stp.rs` does not map reads as 500 (147-156).
- **What reaches these handlers, and what bounds them.**
  - The relay forwards every `/d/{serial}/api/*` path but `ws`, `events` and the STP chunks as an `http.request` frame into the unit's own router (`tunnel/relay.rs:641-662, 675-758`). The unit awaits that router with no timeout (`tunnel/client.rs:2441-2445`); the 55 s covers the body only, and a body over 8 MiB is answered 502. The legacy `tunnel.file.read` calls `get_file` (2530-2554) and `gx.download.init` calls `init_download` (2931-2940), with no timeout; nothing in this repository sends either.
  - The unit runs relay messages under a semaphore of 32 permits (`tunnel/client.rs:1431`), the tunnel's only bound: its router is taken before the LAN port's `ConcurrencyLimitLayer` (`main.rs:1073-1077, 1102-1107`). Every message but the relay's shutdown, pongs, register acks and pings holds a permit for its whole run, as does every binary frame (1594-1659). Pings are answered inline, and any message from the relay refreshes the pong clock (1589-1592, 1618-1625). A unit whose 32 permits are held by reads that never end still looks connected, and answers nothing.
- **Exec children carry secrets in their environment.** An Infra recovery runs with `SCTL_CRED_USER_n` and `SCTL_CRED_PASS_n` from the unit's credential store, for up to 300 s (`infra/monitor.rs:283-296, 340-357`). `POST /api/exec` merges its `env` into the inherited environment (`routes/exec.rs:6-7, 38-39`), and `sctl net` reads `SCTL_SNMP_COMMUNITY` there (`net_tools/mod.rs:279`). `SCTL_API_KEY` in the agent's environment replaces the configured key (`config.rs:876-878`), and every child inherits the agent's environment.
- **Device files act when opened or read.** The agent owns the modem's AT descriptor (`at.rs:1-4`), and the XE300's AT port is shared (`devices/xe300/README.md:18`): another reader takes replies meant for the agent. A block device bypasses every path rule: the WE826's overlay, which holds `/etc/sctl`, is `/dev/mtdblock3` (`devices/we826-qwd/README.md:31`, `routes/info.rs:704`). Opening `/dev/watchdog` starts the hardware watchdog (the kernel's watchdog API, `Documentation/watchdog/watchdog-api.rst`).
- **Pseudo files are regular files by their mode.** On a Linux 6.17 workstation, not a unit: `/proc/net/arp`, `/proc/kmsg`, `/proc/self/environ`, `/proc/self/mem` and `/proc/sysrq-trigger` are regular files of size 0, `/proc/kcore` one of 140,737,471,594,496 bytes and `/sys/class/net/lo/address` one of 4096. `statfs` names `/proc` proc, `/sys` sysfs, `/sys/kernel/debug` debugfs and `/sys/kernel/tracing` tracefs, and `/proc/net` links to `self/net`. A test on the mode alone lets every process secret and `/proc/kmsg` through.
- **The agent already reads procfs and sysfs right, for itself.** `/api/info` and `/api/diagnostics` read `/proc/version`, `uptime`, `meminfo`, `loadavg`, `cpuinfo`, `net/dev`, `mounts`, `sys/kernel/hostname`, `net/tcp` and `net/tcp6`, and `/sys/class/net/<if>/address` and `operstate`, with `read_to_string`, which reads to end of file (`routes/info.rs:113-118, 289-291, 352, 364-365, 596`; `routes/diagnostics.rs:73-76, 119`). nix 0.29 is already built with `fs` (`server/Cargo.toml:32`): it has `O_PATH`, `fstatat`, `statfs` and the procfs, sysfs, debugfs and tracefs magic numbers.
- **The oldest unit kernel takes no `fstat` on a handle.** The WE826 runs Linux 3.3.8 (`devices/we826-qwd/README.md:27`), the XE300 4.14 (ADR-007). `O_PATH` and `AT_EMPTY_PATH` date from 2.6.39, but the kernel takes an `O_PATH` descriptor in `fstat` only from 3.6 and in `fstatfs` only from 3.12 (open(2)). By the man pages, `fstatat` with `AT_EMPTY_PATH` takes it from 2.6.39 (stat(2)), and `/proc/self/fd/<n>` names its file for `readlink`, `statfs` and `open`.
- **Where the agent keeps its keys depends on the layout and the config. The running agent knows both** (`state.rs:79-85`). There are four layouts (`upgrade/install.rs:194-269`, `docs/upgrade.md:71-76`); a RUT241 installs as `gz-tmp` (`devices/rut241/install.sh:96`) and moves to `ramboot` with `devices/rut241/ramboot-migrate.sh`:

  | Layout | Used by | The agent | Rollback set |
  |---|---|---|---|
  | `usr-bin` | generic OpenWrt, the BPIs | `/usr/bin/sctl` | `/usr/lib/sctl/rollback` |
  | `gz-tmp` | the XE300 | payloads in `/usr/local/lib/sctl`, expanded to `/tmp/sctl` | `/usr/local/lib/sctl/rollback` |
  | `ramboot` | the WE826, the RUT241 | fetched into `/tmp/sctl/cache` | `/etc/sctl/rollback` |
  | `systemd` | the relay | `/usr/local/bin/sctl` | `/var/lib/sctl/rollback` |

  - The config file is what `--config` names, else `./sctl.toml` (`config.rs:7, 850-858`): `/etc/sctl/sctl.toml` on units, `/etc/sctl/relay.toml` on the relay.
  - `data_dir` defaults to `/var/lib/sctl`, and `state_dir` to `data_dir`; the environment can override both (`config.rs:186-194, 561-563, 634-644, 885-890`). The XE300 keeps both in `/usr/local/lib/sctl/data`, on the overlay (`devices/xe300/sctl.toml.template:7`). The RUT241 and the WE826 keep `data_dir` in `/tmp/sctl/data` and `state_dir` in `/etc/sctl/state` (their templates, lines 3 and 7). `sctl.toml.bpi` and the relay's example set neither.
  - `state_dir` holds the credential store `infra-secrets.json`, the Infra config `infra-monitor.json` (with any SNMP community a pushed config carries), the TLS pins and the upgrade state, created owner-only (`infra/mod.rs:339-343`, `main.rs:750-765`, `upgrade/state.rs:211-213`). `data_dir` holds the safe-mode flag, `last_panic.log`, the tunnel history and the console journals, under `sessions/` (`sessions/journal.rs:3`). Journals are on by default (`config.rs:195-197`); the unit templates (line 8) and the relay's example (`server/relay.toml.example:28`) turn them off, and `sctl.toml.bpi` leaves them on.
  - Copies of the config, keys included, sit outside `/etc/sctl`: `<rollback_dir>/sctl.toml` after every managed upgrade, whatever the config's own name (`upgrade/stage.rs:651, 712-721`); the install scripts' `/tmp/sctl.toml.backup.<stamp>` (`devices/xe300/install.sh:226`, `devices/rut241/install.sh:87`, `devices/we826-qwd/install.sh:365`); and, until the next boot, `sctl.toml` and a copy of `state_dir` in `/tmp/sctl-we826-refresh-rollback` after the WE826's one-time move (`devices/we826-qwd/ramboot-refresh.sh:110, 128, 937-938, 1012`).
- **What the fleet already refuses.** Since fleet TRD-35 slice 1 (2026-10-21), the fleet's proxy file routes (`GET files`, `GET files/raw`, `POST stp/download`) and its assistant's `read_file` refuse, for everyone and whatever the use: `etc/sctl`, `var/lib/sctl`, `usr/local/lib/sctl/data`, `etc/wireguard`, `etc/netage-server`, `etc/dropbear`, `.ssh`, `etc/shadow`, `etc/shadow-`, `proc/<pid>/cwd`, and the names `infra-secrets.json*` and `sctl.toml*`; and for reads and writes, not listings: `proc/<pid>/environ`, `mem`, `fd` and `map_files` (these and `cwd` also under `task/<tid>`), `proc/kcore`, `proc/kmsg`, `proc/sysrq-trigger`, and anything under `/dev`, directly or through a process's root. It matches a rule's segments anywhere in the normalized path (`/overlay/upper/etc/sctl/...`) and leaves resolving links on the unit to the agent. Its assistant's output masks the unit's WireGuard key, which provisioning writes into `/etc/config/network`; the file itself is not refused.
- **Paths the fleet does not see.** The staff path, sctl MCP's `device_file_read`, calls the agent's `GET /api/files` on the LAN port or through the relay, with no range (`mcp/src/client.rs:141-162`, `mcp/src/tools.rs:841-858`). Anyone with a unit's key can call the agent the same ways. There the agent's own gate is the only one.
- **Not an authorization boundary.** The agent has one pre-shared key per server and no per-user identity (`server/docs/REVIEW.md:33-37`). It usually runs as root (`docs/guide.md:472`); procd starts it with no user (`devices/xe300/sctl.init:51-56`). `POST /api/exec` can read whatever a file route refuses.
- **The wire contract.** `size` is the total file size, and `truncated` says the file goes on past the returned bytes (`docs/http-api.md:317-348`). `files/raw` has no size cap (382-394). The file errors are `400` `INVALID_PATH`, `IS_DIRECTORY` and `FILE_TOO_LARGE`, `403` `PERMISSION_DENIED`, `404` `FILE_NOT_FOUND` and `500` `IO_ERROR` (`error.rs:69-115`, `docs/errors.md:85-123`); none says the path is refused or not a regular file. A read is logged as `FileRead` only after it succeeds (`routes/files.rs:221-238`); a refusal leaves no entry.
- **Other reads are not general file reads.** `/api/fetch` takes only `http` and `https` (`routes/fetch.rs:277-281`). Playbooks are read only inside `playbooks_dir`, under a validated name (`routes/playbooks.rs:214-224`). A listing uses `lstat` and opens no file: a listing of `/proc/<pid>/fd` shows names and link targets, never content (`routes/files.rs:362-432`).

## 3. Decision

1. **A read reads what is there, under a cap.** On a regular file `GET /api/files` reads until it has the size its stat gave (from the offset, within the cap) or the file ends: `size` stays that size, and a file over the cap with no range is refused before it is read (`FILE_TOO_LARGE`). On a pseudo file (decision 3) it reads until `read()` returns 0 or the cap is reached: `size` counts the bytes to where it stopped, and `truncated` is true when the cap stopped it. The cap is `max_file_size`, or the request's `limit` below it. Through the relay it is at most 4 MiB, half the tunnel's 8 MiB body (`tunnel/client.rs:2394`), so the answer fits even as base64; one that still would not is refused with `FILE_TOO_LARGE`, not left to the tunnel's 502.
2. **A file is judged before it is opened, and only a regular file is opened.** The agent first takes a handle on the path that opens nothing (`O_PATH` and `O_CLOEXEC`, links followed). From it, the agent reads the real path (`readlink` of `/proc/self/fd/<n>`), the type and link count (`fstatat` with `AT_EMPTY_PATH`) and the filesystem (`statfs` of `/proc/self/fd/<n>`), and applies decisions 3 and 4. None of these opens the file, and each works on the WE826's kernel (section 2). Only then does the agent open that same file through `/proc/self/fd/<n>`, read-only, with `O_NONBLOCK`, `O_NOCTTY` and `O_CLOEXEC`. The file read is the file judged.
   - A FIFO, a socket, a character device or a block device is refused and never opened (`NOT_A_REGULAR_FILE`): no read waits for a writer, takes a modem's replies, starts a watchdog or reads the flash under the filesystem.
   - A file with no link left (`st_nlink` 0: deleted, or a memory file a process holds) answers as not found, whatever its real path says.
3. **On procfs and sysfs only a short list is read. On debugfs and tracefs nothing is.** The filesystem is the one `statfs` names. On procfs and sysfs the agent reads only these paths, matched as asked:
   - `/proc/net/arp`, `/proc/net/route`, `/proc/net/dev`, `/proc/net/tcp`, `/proc/net/tcp6`;
   - `/proc/meminfo`, `/proc/loadavg`, `/proc/uptime`, `/proc/cpuinfo`, `/proc/version`, `/proc/mounts`, `/proc/sys/kernel/hostname`;
   - `/sys/class/net/<if>/address` and `/sys/class/net/<if>/operstate`.

   That is what the agent already reads about the system for itself, plus the neighbour and route tables. The links inside procfs and sysfs are the kernel's own (`/proc/net` is `self/net`), so a path on the list leads where it says. Everything else there is refused (`PROTECTED_PATH`), `/proc/<pid>/cmdline`, `/proc/<pid>/maps` and `/proc/kallsyms` included. The list lives in one place in the code; widening it is a change that says why. A regular file on any other filesystem is read as decision 1 says, up to its size.

   Whatever the list holds, these are refused wherever they appear in the path as asked or in the real path, `<pid>` being a number, `self` or `thread-self`: `/proc/<pid>/environ`, `mem`, `cwd`, `fd` and `map_files`, each also under `task/<tid>`, and `/proc/kcore`, `/proc/kmsg` and `/proc/sysrq-trigger`. A test pins that no entry of the list can match them.
4. **The agent refuses its own keys by real path, wherever it is installed.** It protects these directories:
   - `/etc/sctl`: every layout's config, `install.json` and ramboot files, and the RUT241's and the WE826's state and rollback set;
   - `state_dir`;
   - `data_dir` when it is also `state_dir` (the XE300, and the repository's BPI and relay configs); otherwise its journal directory, `<data_dir>/sessions`;
   - the rollback directory `install.json` names.

   Each is taken as configured and as its real path, resolved again at each read, so a directory made after start (the rollback set, the journals) is covered once it exists. A read whose path, as asked or as resolved, lies under one of them is refused (`PROTECTED_PATH`). Each is also matched as a run of path components anywhere in the path, so the same file reached through the overlay's upper directory (`/overlay/upper/etc/sctl/...`) or `/rom` is refused too. The config file the agent was started with is refused wherever it is. So is any file whose name begins with that file's name, with `sctl.toml` (the rollback copy's name), with `infra-secrets.json` or with `infra-monitor.json` (the Infra config, which holds the SNMP communities a pushed config carries): the install scripts' backups, the credential store's temporary file, and the copies the WE826's move leaves in `/tmp`.

   The set follows the running agent, not a table of models; the relay's own agent follows the same rules. Playbooks keep their own route, and the payloads, which hold no keys, stay readable.
5. **One gate for every read.** `GET /api/files`, `GET /api/files/raw` and gawdxfer's `init_download` call the same gate before they open anything, so the relay's passthrough, `tunnel.file.read` and `gx.download.init` inherit it. `TransferManager` is given the gate when it is built.
   - `files/raw` and gawdxfer move only regular files on a filesystem that reports their size, so not on procfs or sysfs. A listed pseudo file is refused there (`NOT_A_REGULAR_FILE`, the message naming the filesystem); `GET /api/files` reads it. An empty file is still one empty chunk.
   - `files/raw` streams exactly the size its stat gave, and a transfer's hash reads exactly that size.
   - A download takes its place under `max_concurrent_transfers` before its hash (`MAX_TRANSFERS` past it), so at most that many hashes run.
   - A chunk is read only from the file that was hashed: the same device and inode, still a regular file. Otherwise the transfer fails with `FILE_CHANGED`.
6. **Two refusal codes.** `PROTECTED_PATH` (403) refuses the agent's keys, a process's secrets, a kernel stream, a pseudo file not on the list, and any debugfs or tracefs file. `NOT_A_REGULAR_FILE` (400) refuses a FIFO, a socket, a character or block device, and a listed pseudo file on `files/raw` or in a transfer. The `PROTECTED_PATH` rules come first, so a path they refuse gets that code on every route. The message names the rule or the filesystem, never the content. Both codes enter `server/src/error.rs`, both sections of `docs/errors.md` and the STP status map in `server/src/routes/stp.rs`.
7. **A refusal is recorded on the unit.** It is a `FileRead` entry in the activity feed. Its summary says the read was refused, and its detail names the rule. There is no new activity type.
8. **Reads only, and not a boundary.** Writes, deletes and listings do not change here. A listing opens no file, and a write renames a temporary file over its target (`routes/files.rs:492-533, 847-859`, `gawdxfer/manager.rs:747`), so it opens no device, though a rename can replace a device node; the fleet refuses writes into `/dev`. The unit's other secrets (the WireGuard key in `/etc/config/network`, the SSH keys, the password hashes) are the fleet's to refuse or mask: the agent keeps no list of a firmware's secrets. Exec stays the way to read what this gate refuses, recorded as exec. The gate keeps routine reads away from secrets, and keeps a read from harming the unit.

## 4. Consequences

- `/proc/net/arp` reads whole. On a unit that runs 0.6.12, the neighbour table needs no exec.
- A sysfs file reads with its true length and no false `truncated`. On the LAN port a regular file over 2 MiB reads whole where the cap allows it (the BPIs, the relay).
- Through the relay, on the BPIs and the relay (the 50 MB default), a file over 4 MiB asked with no range is refused (`FILE_TOO_LARGE`) where today it returns its first 2 MiB, `truncated`. MCP's `device_file_read` and the fleet's assistant ask no range (fleet `deviceReadFile`), so they get the refusal the 2 MiB units already give. sctlin asks 1 MiB above 1 MiB and shows `size` and `truncated` as given (`web/src/lib/components/FileBrowser.svelte:247-253, 274-275`). No client must change.
- No read of a FIFO, a socket, a device or a kernel stream can start, and a read of a regular file ends with the file unless its filesystem stalls (a network or FUSE mount). At most `max_concurrent_transfers` hashes run, each bounded by its file's size; a large one still holds its handler while it runs.
- `/proc/<pid>/environ` and the agent's keys, with their copies, are refused on every file-read route of the agent (the JSON read, `files/raw`, transfers), on the LAN port, through the relay and through MCP. Exec still reads them, and a key put in a service unit's environment is outside the gate.
- On the XE300, the BPIs and the relay, a file read no longer serves `last_panic.log` or the tunnel history; staff read them through exec. The RUT241 and the WE826 still serve them.
- Docs: `docs/http-api.md` (the codes, `size` on a pseudo file, the relay's 4 MiB), `docs/errors.md` (the codes), `docs/config.md` (`max_file_size` also ends a pseudo file's read), `docs/safe-mode.md` (the panic log through exec), `docs/guide.md:107` (the key in the config file, not in a systemd `Environment` line), `SECURITY.md` and `server/docs/REVIEW.md` (the gate), and the module doc at `routes/files.rs:14` (50 MB). No new config key, no new dependency.
- It ships in 0.6.12 (TRD-9), through the fleet's rollout, never on LTE. What a unit downloads depends on its target (TRD-9 section 5): about 3.9 MB of gzipped payloads for a `mips_24kc` unit (the XE300, the WE826), plus 1.3 MB of loader libraries on a WE826 when they change, and about 7.4 MB of raw binaries for a `riscv64` unit. The other targets are measured with the release. The fleet's rules, the product's policy, shipped first and stay: they also cover units that do not run 0.6.12 yet. Until a unit runs 0.6.12 it keeps today's behaviour, and staff on the direct paths read `/proc`, `/sys` and `/dev` only through exec.

## 5. Rejected alternatives

- **Reading to end of file alone.** It would open `/proc/<pid>/environ`, `/proc/kmsg`, FIFOs and devices on the JSON route, as `files/raw` and gawdxfer already do.
- **A test on the mode alone.** Every procfs and sysfs file is a regular file by its mode.
- **A deny-list on procfs and sysfs.** procfs grows with the kernel, and an entry a deny-list misses is read. The agent needs about a dozen files.
- **`stat`, then open.** Between the two, a path can be swapped for a device, and the open then acts on it. A handle that opens nothing leaves no such gap.
- **A read deadline instead of the gates.** A read blocked in a blocking thread cannot be cancelled: the deadline frees the tunnel permit, but each such read leaks a blocked thread. The gates keep the read from starting.
- **Clients asking a range instead of the relay's cap.** MCP and the fleet could send a `limit`, but any other caller with the key could still make the unit build a 50 MB answer that the tunnel then drops.
- **The fleet's rules alone.** The staff path and a direct holder of the key never pass through them, and the fleet does not resolve links on the unit.
- **The fleet's whole list in the agent.** The agent refuses what it owns and what harms the unit; a partial list of a firmware's secrets would read as complete.
- **All of `data_dir` on every unit.** On the RUT241 and the WE826 it holds no key: their state is in `/etc/sctl/state`, and journals are off. Refusing it would hide the panic log and the tunnel history for nothing.
- **Comparing each opened file with the key files' device and inode.** Only someone with exec can make a hard link to a key, and exec reads the key anyway. An atomic rewrite also changes the inode.
- **A list in the config.** A unit's config could widen it. The list is code, changed with a reason.
- **Pseudo files on `files/raw`, buffered, or hashed for a transfer.** The JSON read already serves these small text files, with its cap and `truncated`.

## 6. What TRD-9 verifies on a bench unit

Before the rollout, as part of TRD-9's acceptance of its file reads:

- On a WE826 (Linux 3.3.8) first, then each other unit kernel: the `O_PATH` handle, `fstatat` with `AT_EMPTY_PATH`, `readlink` and `statfs` of `/proc/self/fd/<n>`, and the reopen through it.
- Whether `/var` is a link to `/tmp` on the BPIs, so that `/var/lib/sctl` is also `/tmp/lib/sctl`. The bench reads the credential store by both paths and sees both refused.
- Whether `/proc/kcore` exists on each unit kernel and on the relay host, whose unit sets `ProtectKernelTunables` (`server/files/sctl-relay.service:24`): a listing, never a read. Where it exists, a ranged read can return kernel memory until the unit runs 0.6.12.

## 7. Settled questions

Each question this ADR left open, with its answer (2026-10-21).

1. **The relay's cap.** Settled: 4 MiB stands, half the tunnel's 8 MiB body, so an answer fits even as base64 (decision 1).
2. **A stopgap on the relay before 0.6.12.** Settled: none. The relay's systemd unit is not changed to guard its files: that would be a change by hand to production, and 0.6.12 makes it needless.
3. **The panic log and the tunnel history where `data_dir` is `state_dir`** (the XE300, the BPIs, the relay). Settled: staff read them only through exec in this release. Accepted.
4. **Firmware secrets and writes.** Settled: in this release the agent refuses no firmware key file (the WireGuard key, the SSH keys, the password hashes) and no write into `/dev` or `/proc`. Decision 8 stands: those are the fleet's to refuse.
5. **The rollout.** Settled: never on LTE. Before 0.6.12 rolls out, the fleet's rollout engine fails closed: a unit whose path is not known to be wired is busy. Until that ships, units on a vehicle or placed nowhere are held. A unit only ever on cellular gets the release only when a person releases its hold (TRD-9 section 5).
6. **What the release costs a unit.** Settled: each target's own download, as TRD-9 section 5 measures it, not one number for every unit.
